XRTL

XRTL means XPascal Extended RunTime Library. Do not abbreviate this phase as XRT.

Architecture And Test Contracts

  • Shared Architecture: layering, dependency direction, shared ownership, and no-duplication rules.
  • Test Strategy: unit, smoke, contract, adapter, and platform validation expectations.

Development Order

  1. xpc build closeout.
  2. XCLI project creation.
  3. XRTL planning gate: shared architecture, per-library docs, dependency provenance, and test strategy.
  4. XRTL.Core accepted design gate.
  5. XRTL.Core v0 implementation.
  6. Dependency provenance gate before database/web research.

Per-Library Documentation Rule

Every XRTL library gets its own documentation file when it is created. The file should live under this directory and cover purpose, public API, examples, tests, platform notes, dependencies, and provenance links.

Initial Library Plan

Library Role Implementation Gate
XRTL.Core Result/status, error records, option/capability shapes, and shared primitives. Implemented through issue #34 and PR #35 with three-platform validation.
XRTL.Time Clocks, durations, timeouts, timestamps, and deterministic test clocks. Implement before timeout-heavy Process, HTTP, or Database features.
XRTL.Diagnostics Structured diagnostic events, scopes, trace ids, and safe human-readable failures. Implement before library-specific logging appears.
XRTL.Config Typed settings, layered config sources, and secret redaction markers. Implement before Database/Web connection, port, or credential settings.
XRTL.Collections Small shared collections and deterministic iteration helpers when FPC defaults are not enough. Only add helpers proven useful by at least one library contract.
XRTL.Text UTF-8 policy, line endings, escaping, and shared formatting helpers. Implement before generated files, HTTP headers, or diagnostics duplicate text helpers.
XRTL.IO Paths, files, streams, directories, and temporary workspaces. Implement before XCLI generated-project code grows more filesystem logic.
XRTL.Process Process execution, executable lookup, OS/CPU detection, and exit-code contracts. Requires careful platform tests because prior macOS Pascal process execution crashed.
XRTL.Data Driver-neutral data values, fields, parameters, result iteration, and data errors. Implement before Database adapters to prevent driver types leaking into public APIs.
XRTL.Database SQL connection, transaction, adapter, and driver capability boundaries. Issue #40 starts local SQLite over SQLDB only. Network databases are deferred.
XRTL.HTTP HTTP request/response, headers, status codes, server/client transport contracts. Issue #41 compares FCL-Web and fphttpserver, including fork/modification credit strategy.
XRTL.Web Routes, middleware, request context, and application web composition. Issue #42 designs provider-neutral middleware and routing inspired by Rack/Horse; database usage remains optional and explicit.

Library Documentation Template

Section Required Content
Purpose What problem the library solves and what it deliberately does not solve.
Public API Units, main types, functions, command interactions, and stability expectations.
Examples Minimal usage examples that can become tests or smoke fixtures.
Tests Unit tests, smoke tests, platform matrix, and failure cases.
Dependencies Internal and third-party dependencies, with links to provenance records.
Wrap Rationale If wrapping open source, explain why wrapping is needed, what is wrapped, and why direct use was not chosen.
Future Compatibility Known extension points and risks that affect long-term survival.

Initial Candidate Areas

  • Database access candidates: PostgreSQL, MySQL, SQLite, and Firebird when suitable maintained Pascal/FPC integration options are confirmed.
  • Web server candidates: practical Pascal/FPC-compatible HTTP server libraries with cross-platform behavior on Windows, macOS Apple Silicon, and Ubuntu 26.04.
  • Candidate provenance, status, and adoption gates live in Dependency Provenance.

No-Duplication Rule

Before implementation, every library must check Shared Architecture. If a helper, type, config rule, diagnostic shape, data value, path helper, timeout, or HTTP concept already belongs to another library, use that shared owner or open a refactor issue. Do not grow duplicated mini-frameworks inside separate libraries.

Quality Bias

XRTL should not rebuild what active, compatible open source already solves well. It also should not become a fragile pile of wrappers chosen only because they are fast to assemble. Long-term maintainability, testability, and licensing clarity come first.
