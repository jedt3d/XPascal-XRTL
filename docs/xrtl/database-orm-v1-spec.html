XRTL.Database ORM V1 Specification

Status: accepted specification from issue #62, now being implemented by issue #64. This document turns the completed ORM mapping primitives from issue #60 into the staged ORM V1 contract.

Product pitch: XRTL ORM should give Pascal developers the business-app productivity they expect from classic data-aware tooling, but with a clean modern shape: explicit mappings, predictable SQLite persistence, testable sessions, simple repositories, and enough caching to make common CRUD screens feel fast without hiding state behind framework magic.

Executive Summary

ORM V1 stays local-first and SQLite-only while becoming complete enough to power real application screens: create, read, update, delete, migrations, repositories, transaction-scoped sessions, identity-map caching, metadata-backed attachments, and a future bridge into XRTL.Data / MVVM data sources.

The design benchmark is SQLModel plus SQLAlchemy: SQLModel is the approachable application-facing model used in FastAPI documentation, while SQLAlchemy provides the deeper architectural split between Core, ORM, Session, Unit of Work, and Identity Map. XRTL should learn from those ideas without copying Python APIs or source code. ZeosLib remains a Pascal provider/component reference, not the ORM benchmark.

Decisions For V1

Decision V1 Position
Database scope SQLite only, through the existing SQLDB-backed XRTL provider facade. PostgreSQL, MySQL/MariaDB, Firebird, and other network databases stay out of scope.
Architecture style Data Mapper plus Repository and Session/Unit of Work. Do not implement Active Record as the primary public model.
API posture Explicit, Pascal-native, testable, and small. Prefer boring calls that are easy to debug over clever reflection-heavy behavior.
Mapping strategy Start with explicit schema/field mappings. Reflection, attributes, code generation, and schema introspection are later conveniences, not V1 foundations.
Caching Use 80/20 caching first: schema cache, generated SQL cache, and session identity map. Avoid global query result caching in V1.
Attachments File upload/storage is a separate layer. ORM stores metadata and relationships only; it must not own raw file bytes or upload transport.
External code Clean-room implementation. External projects may be credited as design references after provenance review, but no source, API text, or docs are copied into XRTL.

Goals

  • Support the common local SQLite business-app lifecycle: create tables through migrations, insert records, find by id, query lists, update records, delete records, and wrap changes in a transaction.
  • Make ORM usage feel coherent with the existing XRTL.Database stack: provider facade, migrations, SELECT builder, raw mapping, dataset abstraction, and Core result/error contracts.
  • Give application code a stable place for persistence behavior without leaking SQLDB, SQLite3Conn, TSQLQuery, TSQLTransaction, TField, or TDataset.
  • Make common CRUD screens and future data-aware UI components easy to build without committing to Delphi/Lazarus compatibility.
  • Keep enough explicitness that agents and maintainers can inspect mappings, generated SQL, cache state, and transaction boundaries.
  • Document every public ORM slice with examples and tests before moving to unrelated XRTL areas.

Non-Goals

  • No network database providers in this phase.
  • No attempt to clone SQLAlchemy, SQLModel, Django ORM, ActiveRecord, ZeosLib, mORMot, Delphi datasets, or Lazarus components.
  • No global hidden session, process-wide transaction, or automatic lazy loading by default.
  • No file-byte caching, upload HTTP handling, virus scanning, image processing, or object-storage client inside ORM.
  • No schema-diff migration engine, down migration framework, relationship auto-discovery, code generator, or full query language in the first V1 slices.
  • No raw SQL string interpolation helpers that bypass parameter binding.

Benchmark Lessons

Reference What XRTL Should Learn What XRTL Should Avoid
FastAPI + SQLModel Simple application-facing model, strong docs, readable examples, and close fit between persistence objects and API/data validation stories. Do not copy Python type-annotation syntax or combine all concerns too early. Pascal may need clearer separation between persistence schema, DTOs, ViewModels, and UI data sources.
SQLAlchemy Core/ORM Keep a strong lower layer separate from ORM. XRTL already has provider, migration, query builder, and raw mapping primitives; ORM should compose those instead of bypassing them. Do not expose an enormous expression language in V1. Keep the first query/update surface narrow and testable.
SQLAlchemy Session / Unit of Work Use an explicit session boundary for identity map, pending changes, flush, commit, and rollback behavior. Do not hide database writes behind surprising implicit flushes before the mental model is documented and tested.
ZeosLib Useful Pascal reference for provider breadth, component integration, and long-lived database ecosystem concerns. Do not treat Zeos as the ORM design benchmark. It is a provider/component candidate with license obligations to review before any adoption.

Layering

Application / ViewModel
  - owns screen workflows, validation messages, commands

Repository
  - owns application-specific persistence methods
  - calls ORM Session and Mapper

ORM Session / UnitOfWork
  - owns transaction boundary, identity map, dirty changes
  - uses Mapper and Provider facade

ORM Mapper / Schema
  - owns table/field/id mapping and generated SQL
  - uses Query Builder, Parameters, Raw Mapping

XRTL.Database Provider
  - owns SQLite connection, transactions, execution, raw rows

SQLDB / SQLite
  - implementation detail only

Public Concepts

Concept Responsibility First Practical Shape
Schema Defines table, id column, and field mappings. Extend the existing TXrtlDatabaseOrmSchema with insert/update/delete metadata and optional table creation hints.
Field Maps application field name to database column, value kind, nullability, and write behavior. Extend TXrtlDatabaseOrmField with required/nullable/default/write flags.
Record Stores one mapped row as XRTL-owned values. Keep TXrtlDatabaseOrmRecord as the first container; later allow typed object adapters.
Mapper Converts between records and SQL operations. Add CRUD operations over the provider facade. No direct SQLDB calls.
Repository Application-facing persistence API for one aggregate or screen. Thin class wrapping mapper/session calls, with names such as FindById, List, Save, Delete.
Session Transaction-scoped unit of work and cache boundary. Explicit Begin, Commit, Rollback, Find, Save, Delete, and Clear.
Identity Map Ensures the same table/id loaded within one session resolves to the same cached record snapshot. Key by normalized schema id plus int64 primary key. Clear on rollback and explicit clear.
Change Set Tracks new, dirty, and deleted records before flush/commit. Simple explicit registration first: Insert, Update, Delete; automatic dirty tracking can come later.
Attachment Metadata Records file identity, storage URI, owner, size, hash, and media type. ORM maps metadata rows only. Storage/upload code lives outside ORM.

CRUD Contract

The first write-side ORM surface is deliberately small. It supports one-table entities with an int64 id, text/int64/null values, explicit parameters, and SQLite-generated ids.

// Current Pascal shape.
Schema := TXrtlDatabaseOrmSchema.Create;
Result := Schema.Configure('customers', 'id');
Result := Schema.AddField('id', 'id', False, False);
Result := Schema.AddField('name', 'name', True, True);
Result := Schema.AddField('email', 'email', True, True);
Result := Schema.AddField('statusId', 'status_id', True, True);

Mapper := TXrtlDatabaseOrmMapper.Create;

Record := TXrtlDatabaseOrmRecord.Create;
Record.SetText('name', 'Ada');
Record.SetText('email', 'ada@example.test');
Record.SetInt64('statusId', 1);

Result := Mapper.Insert(Connection, Schema, Record, Id);
Result := Mapper.FindByInt64Id(Connection, Schema, Id, Record);
Record.SetText('email', 'ada@xpascal.test');
Result := Mapper.Update(Connection, Schema, Id, Record);
Result := Mapper.DeleteByInt64Id(Connection, Schema, Id);

Repository Contract

Repositories should provide the first user-friendly persistence layer without forcing application code to hand-roll SQL for every screen. A repository is application-specific; XRTL provides base pieces and patterns, not magic generated domain classes in V1.

type
  TCustomerRepository = class
  private
    FSession: TXrtlDatabaseOrmSession;
  public
    function FindById(const Id: Int64; const OutRecord: TXrtlDatabaseOrmRecord): TXrtlResult;
    function ListActive(const OutDataSet: TXrtlDatabaseDataSet): TXrtlResult;
    function Save(const Record: TXrtlDatabaseOrmRecord): TXrtlResult;
    function DeleteById(const Id: Int64): TXrtlResult;
  end;

This lets sample apps teach clear code first. Later code generation or typed generic repositories may reduce boilerplate after the pattern is proven on all three platforms.

Session And Unit Of Work

The session is the main ORM boundary. It owns one database connection reference, one optional active transaction, an identity map, pending changes, and a mapping registry.

Behavior Rule
Begin Starts an explicit database transaction through the provider facade. Nested sessions are out of scope.
Find Checks the identity map first for table/id. On miss, queries through mapper, stores the snapshot, and returns it.
Insert Registers a new record or writes immediately depending on the first implementation slice. Prefer explicit behavior over hidden flush.
Update Writes only mapped writable fields. Detect missing id and missing required fields before SQL execution.
Delete Deletes by schema/id and removes that key from the identity map.
Commit Flushes pending changes if the session supports deferred writes, commits the provider transaction, and keeps or clears cache according to documented policy.
Rollback Rolls back the provider transaction, clears pending changes, and clears identity-map entries loaded or changed during the transaction.

80/20 Caching Plan

V1 should add caching where the benefit is high and the correctness risk is low. The first cache types are structural and session-scoped. Global query result caching is deliberately deferred.

Cache Scope Benefit Invalidation
Schema / mapping cache Process or registry, immutable after registration. Avoid repeated normalization and validation of table/field mapping. Clear only when registry is explicitly rebuilt. Reject mutation after a schema is registered.
Generated SQL cache Mapper or schema registry. Reuse deterministic SELECT/INSERT/UPDATE/DELETE SQL for the same schema and operation. Key by schema revision and operation. Clear if schema registry is rebuilt.
Session identity map One ORM session. Avoid duplicate reads and coordinate changes to the same record in one workflow. Evict by table/id on update/delete; clear on rollback, session clear, or close.
Small lookup cache Optional repository-level helper, not default ORM behavior. Useful for status lists and lookup tables in business screens. Manual TTL or explicit clear only. Not part of the first core ORM implementation.

Do not cache raw file bytes in ORM. Do not cache arbitrary query results in V1. Do not share mutable record instances across sessions.

Attachment And Upload Boundary

File attachment support is required at the product-design level, but upload/storage is not ORM's job. The correct split is:

Layer Owns Does Not Own
Storage / Upload layer Receiving streams, staging files, hash calculation, size limits, media-type sniffing, final storage URI, cleanup of abandoned staged files. Domain relationships, ORM sessions, or object graph behavior.
ORM / Database layer Attachment metadata rows, ownership relationship to application records, migrations for metadata tables, transaction around metadata writes. HTTP multipart parsing, raw file-byte caching, object-store SDKs, virus scanning, or image processing.
Application / ViewModel layer User intent: attach, replace, remove, validate required documents, show upload progress, and present errors. Low-level file layout or database driver calls.

Attachment Metadata Shape

xrtl_attachments
  id             integer primary key
  owner_type     text not null
  owner_id       integer not null
  file_name      text not null
  media_type     text
  size_bytes     integer not null
  sha256         text not null
  storage_uri    text not null
  state          text not null
  created_at_utc text not null

The table name, owner fields, and timestamp representation may change during implementation, but the principle must not: ORM maps metadata and relationships; storage owns bytes.

Attachment Flow

  1. Application receives or selects a file and passes a stream/path to the storage layer.
  2. Storage layer writes to a staging location, computes SHA256, detects or receives media type, and returns a storage descriptor.
  3. Application opens an ORM session and writes the domain record plus attachment metadata in one database transaction.
  4. After metadata commit succeeds, storage finalizes or marks the staged file as retained.
  5. If metadata commit fails, storage deletes the staged file or records it for cleanup.
  6. ORM queries return attachment metadata and storage URI only. File bytes are loaded through storage APIs when explicitly requested.

Relationship Policy

V1 should start with conservative relationships because hidden lazy loading is a common source of hard-to-debug behavior.

  • Support explicit one-to-many lookup by foreign key only after CRUD/session is stable.
  • Do not auto-load relationships by property access in V1.
  • Provide repository methods such as LoadOrdersForCustomer before magic relationship traversal.
  • Use explicit attachment relationship helpers because attachment storage side effects need careful cleanup.

Test Strategy

  • Unit tests: schema validation, field metadata, generated SQL cache keys, identity-map keys, invalid identifiers, missing required fields, and cache behavior.
  • SQLite integration tests: CRUD mapper inserts/updates/deletes rows, transaction rollback restores state, session commit persists changes, and session rollback clears identity-map state.
  • Attachment tests: metadata schema creation, attachment metadata inserts and queries correctly, validation fails loudly, and ORM never loads or caches file bytes.
  • Repository tests: repository wrapper methods produce predictable records and failure results.
  • Cross-platform validation: Windows x86_64, macOS Apple Silicon aarch64, Ubuntu 26.04 x86_64, all with FPC 3.3.1.
  • CI: Windows CI must build and run the new tests for every merged slice. Remote macOS/Ubuntu evidence stays in PR comments or Captain's Log until hosted runners are configured.

Documentation Requirements

  • Each ORM slice updates XRTL.Database, this spec, the issue map, PRD, roadmap, ADRs when needed, and Captain's Log.
  • Each new public ORM type must have a short example in the library docs before the implementation PR is marked ready.
  • Attachment docs must clearly show that storage/upload is a separate layer and that ORM owns metadata only.
  • Cache docs must name the cache scope and invalidation rule. If invalidation cannot be explained simply, the cache is too risky for V1.

Licensing And Provenance

SQLModel and SQLAlchemy are design benchmarks only. Their licenses and docs are recorded so the project can credit the references, but XRTL must not copy implementation, public API wording, documentation text, or examples. ZeosLib remains research-only/deferred unless a later provider issue reopens it with license and platform evidence.

Any storage library, MIME detector, hashing helper, HTTP multipart parser, or object-storage SDK proposed for attachment support must pass the dependency provenance gate before adoption.

Open Questions For Later Slices

  • Should typed entity adapters use Pascal classes, records, interfaces, or generated code after the record-container API proves itself?
  • Should sessions flush immediately on Save in early V1, or queue pending changes until explicit Commit?
  • What timestamp format should the attachment metadata table use before XRTL.Time owns a durable timestamp contract?
  • Should attachment owner identity use owner_type strings, explicit join tables per entity, or both?
  • When XRTL.Data begins, how much of ORM should feed data-aware screens directly versus through repositories and ViewModels?
