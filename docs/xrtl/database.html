XRTL.Database

Status: local SQLite foundation implemented in issue #40. Issue #48 adds public transactions and parameter binding. Issue #50 adds detached raw row/field/value mapping. Issue #52 adds a small app dataset abstraction over detached rows. Issue #54 adds a SQLite-only provider abstraction facade. Issue #56 adds apply-only migration primitives. Issue #58 adds SELECT query builder primitives. Issue #60 adds ORM mapping primitives and completes the local-only feature stack from issue #47. Network databases remain out of scope.

Read the database/web candidate research.

Purpose

Database owns SQL and database adapter behavior while keeping public contracts independent from any single driver stack.

Responsibilities

  • SQLite file and in-memory connection configuration.
  • Open/close behavior for local SQLite databases through SQLDB.
  • Simple execute and scalar query operations for bootstrap smoke coverage.
  • Public transaction control for local SQLite.
  • Text, int64, and null parameter binding without exposing SQLDB parameter types.
  • Detached raw result-set snapshots for local SQLite queries.
  • App-facing cursor-style dataset iteration over detached raw results.
  • SQLite provider metadata and a provider-neutral connection facade that delegates to the SQLite backend.
  • Apply-only migration plans over the provider facade with XRTL-owned metadata.
  • Deterministic SELECT query generation with validated identifiers and XRTL-owned parameters.
  • Explicit ORM schema, field mapping, and read-only row-to-record mapping primitives.
  • Error results through XRTL.Core result/error contracts.
  • Future ORM surface only after a separate issue defines it.

Non-Responsibilities

  • No editable, observable, UI-bound, or SQLDB-backed dataset behavior.
  • No web request lifecycle or route handling.
  • No non-SQLite provider selection, rollback/down migration API, full active-record framework, write lifecycle, relationships, lazy loading, identity map, code generation, or schema introspection in the ORM mapping slice.
  • No PostgreSQL, MySQL/MariaDB, Firebird, or other network database adapters in v0.

Public V0 Surface

Type Or Member Purpose
TXrtlSqliteConnectionConfig Creates file or :memory: SQLite connection configs without exposing SQLDB types.
TXrtlSqliteDatabase.Open / Close Owns local SQLite connection lifecycle and reports failures through TXrtlResult.
TXrtlSqliteDatabase.Execute Runs a non-query SQL statement. The one-argument form uses an implicit transaction; the parameterized overload binds XRTL-owned parameters.
TXrtlSqliteDatabase.QueryInt64 Runs the first scalar query shape needed by bootstrap tests, such as select count(*). A parameterized overload binds text, int64, and null parameters.
TXrtlSqliteParameters Reusable parameter collection for named SQLite parameters. Supports text, int64, and null values.
BeginTransaction / Commit / Rollback Explicit public transaction control. Invalid state transitions fail with XRTL error codes instead of leaking SQLDB exceptions.
TXrtlSqliteValue Represents detached raw SQLite values. The first supported kinds are null, text, and int64.
TXrtlSqliteField / TXrtlSqliteRow / TXrtlSqliteResultSet XRTL-owned raw result mapping types for columns, rows, and field lookup without exposing TField or TDataset.
TXrtlSqliteDatabase.QueryRows Runs a select query and fills a caller-owned detached result set. Parameterized and non-parameterized overloads are available.
TXrtlSqliteDataSet Small app-facing cursor abstraction over detached raw rows. Supports active state, record/field counts, First, Next, Eof, CurrentRow, and ValueByName.
TXrtlSqliteDatabase.QueryDataSet Runs a select query and loads a caller-owned detached dataset. Parameterized and non-parameterized overloads are available.
TXrtlDatabaseProviderCapabilities Describes the current provider kind/name and local capabilities. SQLite is the only provider kind in this slice.
TXrtlDatabaseConnectionConfig Creates provider-neutral connection configuration for SQLite file and in-memory databases.
TXrtlDatabaseConnection Provider-neutral facade that delegates execute/query/transaction behavior to the existing SQLite implementation.
TXrtlDatabaseMigration Defines one explicit migration id, description, and ordered SQL statement list.
TXrtlDatabaseMigrationPlan Stores an ordered migration list and validates duplicate or invalid migration ids before apply.
TXrtlDatabaseMigrationRunner Applies pending migrations through TXrtlDatabaseConnection, records metadata in xrtl_schema_migrations, skips already-applied ids, rejects out-of-order plans, and wraps each migration in a transaction.
TXrtlDatabaseSelectBuilder Builds deterministic SELECT SQL and caller-owned TXrtlDatabaseParameters. Supports validated table/column identifiers, default *, explicit columns, text/int64 equality filters, order direction, and non-negative row limits.
TXrtlDatabaseOrmSchema / TXrtlDatabaseOrmField Defines explicit table/id-column and application-field-to-database-column mappings.
TXrtlDatabaseOrmRecord Stores mapped XRTL-owned values by application field name.
TXrtlDatabaseOrmMapper.FindByInt64Id Uses the provider facade and SELECT builder to map one local SQLite row into an ORM record container.

Initial Candidate Posture

Candidate Current Posture Why
FPC SQLDB Wrapped for local SQLite v0. Built into the FPC ecosystem and provides the SQLDB/SQLite3Conn path. SQLDB and SQLite3Conn remain implementation details, not public XRTL types.
ZeosLib Deferred fallback/future adapter candidate. Broad database support, but license metadata includes LGPL-2.1 plus a separate Zeos-specific license file on the GitHub mirror. Use only if SQLDB gaps justify another provider.
mORMot 2 Deferred candidate for larger server/data stack. Very broad features and active modern Object Pascal scope. Risk is over-adopting a full framework when XRTL needs a narrow first database adapter.

Wrap Rationale

Database should wrap driver stacks behind XRTL.Data contracts because XPascal needs stable diagnostics, config, platform behavior, and test contracts even if the first backend changes. Directly exposing SQLDB, Zeos, or mORMot types would make later backend changes expensive.

Dependencies

Database may depend on Core, Diagnostics, Config, Data, Text, IO, Process, and Time. It must not depend on HTTP or Web.

First Tests

  • database_smoke checks library metadata and SQLite config behavior.
  • database_sqlite_tests creates a local SQLite file, creates a table, inserts rows, queries a count, and verifies error paths.
  • database_transaction_tests verifies public transaction state, commit, rollback, text/int64/null binding, parameter reuse, and binding failures.
  • database_raw_mapping_tests verifies detached result sets, row/field lookup, text/int64/null values, parameterized raw queries, and lookup failure codes.
  • database_dataset_tests verifies detached dataset state, navigation, current value lookup, empty result behavior, raw result loading, and dataset failure codes.
  • database_provider_tests verifies provider capabilities, provider-neutral config, execute/query facade behavior, transaction delegation, raw results, datasets, and invalid/not-open paths.
  • database_migration_tests verifies empty plans, invalid and duplicate ids, transaction guards, idempotent apply, metadata ordering, out-of-order detection, and rollback after failed migration statements.
  • database_query_builder_tests verifies SELECT SQL generation, output parameters, query execution through the provider facade, default columns, ordering, limits, no-result queries, invalid identifiers, duplicate parameters, and invalid limits.
  • database_orm_tests verifies schema validation, duplicate fields/columns, find-by-id mapping, missing records, invalid mapper arguments, and mapped field lookup failures.
  • No PostgreSQL, Firebird, MySQL, or MariaDB tests in v0.
  • Network adapters require later issues with service setup, native client libraries, and credentials documented outside tracked files.

Platform Runtime Notes

  • Windows test hosts need sqlite3.dll on PATH; CI installs the SQLite runtime through the Windows vcpkg image.
  • macOS Apple Silicon normally resolves libsqlite3.dylib from the platform SDK/runtime.
  • Ubuntu validation needs libsqlite3-dev so FPC's SQLite loader can resolve libsqlite3.so.
