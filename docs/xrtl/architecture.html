XRTL Shared Architecture

XRTL is the XPascal Extended RunTime Library. It is not a Delphi, Lazarus, or FPC compatibility clone. The project can reuse good Pascal ecosystem work, but the XRTL structure is owned by XPascal and should be optimized for future survival, testability, and clear public contracts.

Status

This is the planning contract for issue #26. No meaningful XRTL unit should merge until its library documentation file exists and the shared ownership table below has been checked.

The exact Pascal unit names can change in the implementation ADR, but the dependency direction should remain stable unless a later ADR supersedes this plan.

Layer Rules

Layer Libraries Allowed Direction
Foundation Core, Time No dependency on other XRTL libraries. These units define small shared primitives only.
Support Diagnostics, Config, Collections, Text, IO, Process May depend on Core and Time. Must not depend on Database, HTTP, or Web.
Data Model Data May depend on Core, Collections, Text, Time, and Diagnostics. Must not depend on any concrete database driver.
Adapters Database, HTTP May depend on foundation/support libraries. Concrete third-party adapters must stay behind XRTL contracts.
Application Runtime Web May depend on HTTP, Config, Diagnostics, Text, IO, Time, and Core. Database use must be explicit and optional.

Shared Ownership Catalog

Capability Owning Library Duplication Rule
Result status, error record, option/null value, feature flags Core Other libraries may add domain-specific errors, but must use Core status and error shapes.
Clock abstraction, durations, timestamps, monotonic time Time No library should invent its own timestamp or timeout type without first checking Time.
Log events, diagnostic scopes, trace ids, human-readable failure notes Diagnostics Libraries emit diagnostics through this layer instead of writing directly to console output.
Environment variables, config files, layered settings, typed option parsing Config Libraries declare config keys; they do not parse environment strings independently.
Reusable collections, iteration helpers, stable maps/sets when FPC defaults are insufficient Collections Add here only when FPC built-ins do not meet portability, testability, or API consistency needs.
UTF-8/text normalization, line endings, escaping, simple format helpers Text HTTP, Database, and Config may use Text helpers but must not create separate encoding helpers.
Paths, file IO, streams, temp directories IO Process and Web may consume IO paths but must not own filesystem abstractions.
Process execution, exit codes, OS/CPU detection, executable lookup Process Build tools and Doctor-style checks should share this layer once Pascal-side orchestration is safe.
Rows, fields, parameters, data errors, connection-neutral query contracts Data Database adapters translate into Data contracts; Data must stay driver-free.
SQL database adapters and transaction behavior Database Adapter-specific code stays here. Database must not own generic records, logging, config, or HTTP concepts.
HTTP request/response, headers, status codes, server/client transport contracts HTTP Web routing builds on HTTP. HTTP must not know application routes or database services.
Routing, middleware, request context, controller-style composition Web Web owns application composition and should not duplicate lower-level HTTP parsing.

Pre-Implementation Refactor Gate

  1. Open or confirm a GitHub issue for the library.
  2. Update that library's document under docs/xrtl/.
  3. Check the shared ownership catalog for any helper, type, or policy the new library wants to add.
  4. If the helper belongs to another library, either use that library or open a refactor issue before duplicating it.
  5. Update Dependency Provenance before copying, linking, wrapping, or vendoring third-party code.
  6. Add unit, smoke, or contract tests in the same PR as implementation.
  7. Run Windows, macOS Apple Silicon, and Ubuntu validation for platform-affecting behavior.

Wrapper Decision Ladder

  1. Use FPC or standard runtime capability directly when it is stable, cross-platform, and not a leaky user-facing API.
  2. Use an active open source library directly only when its API is already the right long-term public contract for XPascal.
  3. Wrap an open source library when XRTL needs API stability, multiple backend choices, platform-specific behavior, better diagnostics, or license/attribution isolation.
  4. Use a library only as design inspiration when its license, maintenance, API shape, or platform story is not acceptable.
  5. Build custom code only after documenting why existing maintained options do not fit.

First Implementation Bias

Start with narrow, boring, testable primitives: Core status/errors, Time clock abstractions, Diagnostics events, Config parsing, and IO/Process safety helpers. Database and Web should wait until Data and HTTP contracts can keep them from becoming monolithic wrappers around whichever dependency is adopted first.
