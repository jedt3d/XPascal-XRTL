XRTL.Web

Status: planned. No implementation exists yet.

Purpose

Web owns application-level web composition: routing, middleware, request context, handler execution, and web-specific diagnostics.

Responsibilities

  • Route declaration and matching.
  • Middleware order and handler lifecycle.
  • Request context that can carry diagnostics, config, and optional service references.
  • Error-to-response mapping at the application layer.

Non-Responsibilities

  • No low-level HTTP parser or socket lifecycle; HTTP owns transport contracts.
  • No database dependency by default. Database-backed apps must opt in explicitly.
  • No frontend framework, UI toolkit, or template engine in the first plan.

Initial Candidate Posture

Candidate Current Posture Why
Horse Research-only candidate and design reference. Minimal Express-inspired API, MIT license, Lazarus/FPC quickstart, and provider model are attractive. XRTL still needs to decide whether wrapping or independent API design is safer.
Brook Research-only candidate. Pascal microframework with LGPL-2.1 license and broad feature set. Needs maintenance and dependency review before adoption.
mORMot 2 Research-only candidate for full-stack server apps. Powerful ORM/SOA/MVC stack. Risk is locking XRTL.Web to a comprehensive framework before XPascal's minimal web contract is proven.

Wrap Rationale

Web should not expose Horse, Brook, or mORMot as the public XPascal contract until the project proves that doing so preserves long-term survival. A wrapper or inspired independent API can keep route/middleware behavior stable while the HTTP provider changes underneath.

Dependencies

Web may depend on Core, Diagnostics, Config, Text, IO, Time, and HTTP. Database dependency must be optional and documented by a separate issue.

First Tests

  • Route matching tests for literal, parameter, and not-found paths.
  • Middleware order tests.
  • Error mapping tests.
  • Loopback request smoke through the selected HTTP provider.
