XRTL.Core

Status: accepted design gate for issue #32, revised after a release-note-first FPC research pass. Runtime implementation belongs in a follow-up issue and PR.

Purpose

Core owns the smallest shared runtime primitives that let XRTL libraries communicate without depending on each other. It should be boring, stable, dependency-free inside XRTL, and portable across Windows x86_64, macOS Apple Silicon aarch64, and Ubuntu 26.04 x86_64.

Design Position

  • Core is a foundation library, not a utility drawer.
  • Core APIs should be stable enough for every later XRTL library to depend on.
  • Core must not perform IO, process execution, logging, config loading, encoding conversion, database work, HTTP parsing, or web routing.
  • Core should prefer plain records, enums, constants, and small functions over object hierarchies.
  • Core should avoid public exception flow. XRTL libraries return status/error contracts for expected failures.

Compiler Research Notes

Research Point Finding Design Impact
Release stream The latest official stable release remains FPC 3.2.2. The only recent release-style notice found in the last three years is FPC 3.2.4-rc1, a fixes-branch release candidate announced in June 2025. The project pins development snapshot 3.3.1, while upstream notes development versions have no support guarantee and snapshots may contain bugs. Use 3.3.1 intentionally, but keep Core's first implementation on proven language features that compile in the pinned snapshot across all supported platforms. Treat 3.2.4 fixes-branch notes as compatibility signals and trunk-only features as opt-in after tests, not as default style.
Release-note priority Official announcements and mailing-list release notes carry more weight than wiki pages. The 3.2.4-rc1 thread itself noted broken wiki links, so this design uses the announcement text and FPC docs as primary evidence. Future compiler research should cite release announcements, release-candidate threads, official docs, and local compiler validation before citing wiki summaries.
Cross-compilation FPC exposes target CPU/OS options and compile-time target defines. Cross-compiling also changes the target define set and may define FPC_CROSSCOMPILING. Core must not infer behavior from the host machine. Any future platform conditional must key off target/compiler defines and be validated by the three-platform matrix.
Modern records FPC extended records support methods, properties, and operators; ObjFPC mode requires {$modeswitch advancedrecords}. Record methods do not change the record memory layout. Core should use advanced records for value-like APIs such as error/result/option/capability. This is modern Object Pascal without paying class allocation or inheritance costs.
Generics FPC generics are supported but have scope rules: identifiers beyond template placeholders must be known when the generic is declared, and generic code cannot assume fields or methods on an unrestricted template type. Generic Core types are allowed only when self-contained and simple. First implementation may include generic option/value-result shapes, but they must not depend on consumer-specific operations.
Anonymous functions and function references FPC 3.3.1 supports anonymous functions and function references through mode switches, but closure capture has interface-backed behavior and non-trivial performance/ownership implications. Do not use anonymous functions or function references in the first Core implementation. They can become APIs later for callbacks, iterators, or diagnostics only after a focused ADR and platform tests.
Newest trunk experiments Recent trunk work includes features such as record composition and managed-record move optimizations, but they are not needed to express the first Core contract. Do not base Core's first public contract on features that are newer than the project's validation evidence. Prefer readable records and functions that remain easy to debug.

Initial Public Contract

Area Proposed Shape Rationale
Status TXrtlStatus = (xsOk, xsError) and helper predicates such as XrtlStatusOk. One success/failure shape prevents each library from inventing incompatible booleans, integers, or exception conventions.
Error identity TXrtlError record with stable machine fields: Domain, Code, and human field Message. Domain and code are for program decisions; message is for humans and diagnostics. Core does not own logging output.
Result TXrtlResult record containing Status and Error. Value-returning APIs may use generic TXrtlValueResult<T> after cross-platform validation. A non-generic result stays the common denominator; a small generic value-result lets modern APIs avoid separate status/value variables when it remains self-contained.
Presence TXrtlPresence = (xpMissing, xpPresent) plus generic TXrtlOption<T> for optional values. Presence remains the shared low-level marker, while a generic option record provides a modern type-safe API for simple optional values.
Capability identity TXrtlCapability record with Name and Supported, plus optional Detail. Adapters can report backend support without forcing Core to know about databases, HTTP servers, or operating systems.
Version identity Constants for XRTL library contract version, separate from compiler and package version. Consumers need a stable way to reason about the contract a unit was built against.

Resolved Design Choices For V0

Question Decision Reason
Unit name Use flat Pascal unit name xrtl_core for the first implementation. It avoids coupling the first runtime surface to dotted-unit behavior before this repo has its own cross-platform evidence.
Generic option/value result Include simple generic records only if they compile and run on Windows x86_64, macOS Apple Silicon aarch64, and Ubuntu 26.04 x86_64. This gives modern, type-safe APIs while preserving a hard validation gate. If generics fail on any supported platform, Core v0 falls back to non-generic result/presence primitives.
Capability marker Include a minimal TXrtlCapability marker in Core v0. Database, HTTP, Web, and process adapters will need a shared way to report support without forcing those libraries to duplicate capability contracts.
Structured error detail Defer structured error detail, nested causes, and ownership-heavy diagnostics. Core v0 should settle stable error identity first. Detail fields need a later ADR once Diagnostics and Text requirements are clearer.

Proposed Unit Boundary

The library is named XRTL.Core. The first implementation should use a conservative flat Pascal unit name until FPC 3.3.1 dotted-unit behavior is proven in this repository.

src/xrtl/core/
  xrtl_core.pas

tests/xrtl/core/
  core_smoke.pas
  core_result_tests.pas
  core_error_tests.pas

The first unit may contain the whole contract. Split into more units only after the implementation has real pressure to separate error, result, or capability code.

Error Rules

  • Error Domain values should use stable lowercase names such as xrtl.core, xrtl.io, or xrtl.database.
  • Error Code values should be stable machine-readable identifiers such as invalid_argument or unsupported_capability.
  • Error Message values are not stable API and may change for clarity.
  • Core must not store nested heap-owned error causes in the first implementation. Chained errors need a later ADR because ownership rules matter.
  • Expected failures should return TXrtlResult. Exceptions remain reserved for programming errors, compiler/runtime failures, or unrecoverable allocation behavior.

Non-Responsibilities

Concern Owner Core Boundary
Clock, timestamps, durations, timeouts XRTL.Time Core may return result/errors for time functions, but it must not define time primitives.
Logging, trace ids, redacted diagnostic output XRTL.Diagnostics Core defines error shape only. Diagnostics decides how failures are emitted.
UTF-8, escaping, line endings, formatting helpers XRTL.Text Core uses strings but does not own text policy.
OS, CPU, executable lookup, process execution XRTL.Process Core may expose a capability marker shape, but Process owns detection and execution.
Paths, streams, files, temporary directories XRTL.IO Core must not own filesystem abstractions.
Driver-neutral data values and records XRTL.Data Core result/errors can wrap data failures, but data values are not Core primitives.

First Tests

  • Compile smoke for the Core unit on Windows, macOS Apple Silicon, and Ubuntu.
  • Unit tests for status success/failure helpers.
  • Unit tests for error domain/code/message construction and comparison.
  • Unit tests for optional presence markers.
  • Negative test for invalid or empty error identity values if constructors enforce validation.

Open Review Questions

  • None blocking for Core v0. The resolved choices above define the implementation starting point.
  • Follow-up ADR candidates: dotted unit names, structured error detail, callback/function-reference APIs, and Diagnostics-owned rendering.
