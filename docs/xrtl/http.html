XRTL.HTTP

Status: planned. Issue #28 research recommends XRTL-owned HTTP contracts with a first loopback provider over FPC fcl-web/fphttpserver.

Read the database/web candidate research.

Purpose

HTTP owns transport-neutral request, response, header, status, and server/client contracts. It is lower-level than XRTL.Web.

Responsibilities

  • HTTP method, status, header, and body contracts.
  • Request/response parsing policy where XRTL owns the shape.
  • Transport adapter boundary for built-in FPC, mORMot, Indy, or other providers.
  • Loopback smoke testing surface for future Web tests.

Non-Responsibilities

  • No route tree, middleware pipeline, controllers, or templating; Web owns those.
  • No database or ORM dependencies.
  • No TLS policy until a dedicated security issue exists.

Initial Candidate Posture

Candidate Current Posture Why
FPC fphttpserver Recommended first loopback provider behind XRTL.HTTP. Part of the FPC ecosystem and practical for a first self-hosted server smoke, while keeping the public API provider-neutral.
mORMot 2 Deferred high-performance HTTP/WebSocket candidate. Powerful and cross-platform, but broad enough that wrapping only the needed transport is safer than making it the public API.
Indy Deferred protocol/networking candidate. Large protocol suite, but TLS/OpenSSL and FPC integration deserve a dedicated networking issue before adoption.

Wrap Rationale

HTTP should wrap provider-specific servers because Web and CLI tests need one stable request/response contract. Directly exposing a provider would couple XPascal applications to provider-specific lifecycle and platform behavior too early.

Dependencies

HTTP may depend on Core, Diagnostics, Config, Text, IO, Process, and Time. It must not depend on Database or Web.

First Tests

  • Header normalization and status code tests.
  • Request/response body boundary tests.
  • Loopback smoke with the selected provider on Windows, macOS Apple Silicon, and Ubuntu.
