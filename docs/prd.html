Product Requirements Document

This is the living PRD for the XPascal/XRTL bootstrap era. It translates the broader proposal into current product requirements, acceptance expectations, and open product questions.

Document Cadence

  • Update this PRD when an issue changes product scope, user workflow, public CLI behavior, platform support, or milestone priority.
  • Review this PRD before opening a feature PR that changes user-facing behavior.
  • Link relevant GitHub issues and PRs when a requirement is implemented, deferred, or removed.
  • Keep architectural rationale in ADRs; keep product intent and acceptance criteria here.

Current Product Goal

Build a FreePascal-powered, CLI-first application platform with traceable tooling, repeatable bootstrap scripts, and a path toward cross-platform desktop, web, and server development.

Primary Users

User Need Current Requirement
Project maintainer Traceable progress across issues, PRs, CI, and docs. Every non-trivial change starts from a GitHub issue and updates the issue map, Captain's Log, PRD, or ADRs when relevant.
Platform contributor Reliable bootstrap on supported operating systems. Windows x86_64, macOS Apple Silicon aarch64, and Ubuntu 26.04 x86_64 are the initial supported targets.
Pascal developer A predictable CLI and toolchain foundation. xpc version and xpc doctor must report platform and FPC state clearly and fail loudly when FPC is missing or not 3.3.1.
AI coding agent Plain-text source of truth and repeatable checks. Docs, scripts, lock files, and tests must be reviewable and runnable without hidden IDE state.

In Scope Now

  • Pinned FreePascal 3.3.1 bootstrap tooling.
  • xpc CLI skeleton with version and doctor.
  • Manual validation scripts for Windows, macOS Apple Silicon, and Ubuntu 26.04.
  • Windows CI as the first hosted automation path.
  • Issue-first project management with PR closeout evidence.
  • Captain's Log, issue map, roadmap, PRD, and ADR documentation cadence.
  • XRTL library planning gate: shared architecture, per-library docs, test strategy, and dependency provenance before runtime implementation.

Out Of Scope Now

  • macOS Intel support.
  • IDE-dependent workflows.
  • Delphi/Lazarus framework compatibility.
  • Runtime API surface beyond the first CLI/toolchain foundation.
  • Automated GLM integration beyond file-based/manual review exchange.

Open Product Questions

  • When should xpc build move from launcher-managed build orchestration into the Pascal CLI itself?
  • When should XRTL.Core revisit dotted Pascal unit names after flat xrtl_core ships?
  • Should generic option/value-result types remain in Core v0 after three-platform validation, or should they be deferred if compiler behavior is unstable?
  • How much of FPC SQLDB should XRTL.Database expose directly versus hide behind XRTL.Data contracts?
  • Should XRTL.Web wrap Horse, only use it as design inspiration, or defer Web until HTTP contracts are proven?
  • Which validation results must be hosted in CI versus accepted as manual PR evidence during bootstrap?
  • When should GLM move from file-based manual exchange to automation?
