XRTL Database And Web Candidate Research

Status: issue #28 research record. No third-party code is adopted, copied, vendored, linked, or exposed by this document.

Date: 2026-06-12. Scope: Windows x86_64, macOS Apple Silicon aarch64, and Ubuntu 26.04 x86_64 with pinned FreePascal 3.3.1.

Recommendation

  • Database: issue #40 starts XRTL.Database with local database only: SQLite through FPC SQLDB. PostgreSQL, Firebird, and MySQL/MariaDB service tests are deferred.
  • HTTP: issue #41 starts with focused research comparing the broader FCL-Web package against the narrower fphttpserver unit/provider. If code is forked or modified, the fork must preserve upstream credit and document changes.
  • Web: issue #42 starts with an XPascal-owned middleware and routing design, inspired by Rack and Horse where useful, but not copying either public API.
  • Deferred candidates: keep network databases, ZeosLib, mORMot 2, Brook, Indy, and Horse adapters out of scope until a later small issue proves need, licensing, and platform behavior.

Decision Weighting

Criterion Weight Reason
Long-term survival Highest XRTL should own stable public contracts and avoid locking early APIs to a third-party framework's lifecycle.
License clarity High The project must respect upstream copyright, notices, linking terms, and native client library obligations before packaging.
Supported-platform proof High Every candidate must work on Windows, macOS Apple Silicon, and Ubuntu 26.04 with FPC 3.3.1 before adoption.
Feature fit Medium Large feature sets are useful only when they do not pull XRTL into an oversized dependency or duplicated architecture.

Database Candidates

Candidate Evidence License Signal Fit Risk Recommendation
FPC SQLDB / fcl-db FPC documents SQLDB as a uniform SQL layer over supported database-specific connection components. Daily FPC docs list fcl-db units including SQLite3Conn, PQConnection, mysql80conn, and IBConnection. FPC home page states packages and runtime library use a modified Library GPL to allow static linking. Native database client libraries still carry their own obligations. Best first baseline because it ships with the toolchain ecosystem and keeps the initial adapter narrow. Potential old-style TDataset surface, provider-specific quirks, and native client library packaging. Use as first prototype backend behind an XRTL wrapper.
SQLite client library FPC provides SQLite-related packages/units, including SQLite3Conn in fcl-db and lower-level SQLite units. SQLite upstream states SQLite is public domain and does not require a license. Best first local smoke target because it does not need a running service. Native library discovery and version differences across OS packages must be handled by tooling. Use as first local database smoke target.
PostgreSQL via SQLDB/libpq FPC SQLDB examples document switching from Firebird/InterBase to TPQConnection; daily docs show PQConnection uses postgres3dyn. PostgreSQL upstream describes its license as liberal open source, similar to BSD or MIT. Good later network database service because it is popular, mature, and license-friendly. Requires test service setup and native libpq availability per platform. Defer; not part of XRTL.Database v0.
MySQL/MariaDB via SQLDB FPC fcl-db daily docs list mysql80conn; MariaDB Connector/C documents MySQL/MariaDB client connectivity. Oracle MySQL client licensing has GPL/FOSS-exception complexity; MariaDB documents LGPL client libraries for C, Java, and ODBC. Important business-app target, but less clean than SQLite for first validation. Client library selection can change redistribution obligations. Prefer MariaDB Connector/C if it works with FPC SQLDB on all target platforms. Defer; not part of XRTL.Database v0.
Firebird via SQLDB FPC SQLDB examples use TIBConnection for Firebird/InterBase; daily docs show IBConnection depends on ibase60dyn. Firebird documents IPL and IDPL licenses. Valuable Pascal ecosystem target and should remain in later validation. Client library packaging and embedded/server mode choices need explicit platform tests. Defer; not part of XRTL.Database v0.
ZeosLib SourceForge and GitHub mirror describe broad DB support including MySQL, MariaDB, PostgreSQL, Firebird/InterBase, SQLite, Oracle, ODBC, DuckDB, and QuestDB. GitHub mirror reports LGPL-2.1 plus a project-specific COPYING.ZEOS file; official upstream is SourceForge/SVN rather than the mirror. Strong fallback if SQLDB lacks features or compatibility. More code surface, project-specific license file, and official-upstream ambiguity must be resolved before adoption. Defer; keep as fallback/future adapter candidate.
mORMot 2 mORMot 2 documents database, ORM/ODM, HTTP, WebSockets, REST, SOA, MVC, JSON, crypto, logging, and cross-platform FPC support. Upstream documents a disjunctive MPL/GPL/LGPL three-license model. Excellent full-stack candidate for later high-performance server apps. Too much public API surface for the first database layer; could duplicate or dominate XRTL architecture. Defer; evaluate only after XRTL.Database and XRTL.HTTP contracts exist.

HTTP And Web Candidates

Candidate Evidence License Signal Fit Risk Recommendation
FPC fcl-web / fphttpserver Daily FPC docs list fcl-web units including fphttpserver, fphttpclient, HTTPRoute, WebSocket units, JSON-RPC, REST bridge, and SQLDB REST units. Part of FPC/FCL package licensing; verify selected snapshot files before redistribution. Best initial research target because it travels with the FPC ecosystem and includes the narrower fphttpserver provider. FCL-Web is a package family while fphttpserver is a unit/provider; issue #41 must decide whether to wrap, fork/modify, or use as reference. Research FCL-Web versus fphttpserver before implementation.
Horse Horse README describes an Express-inspired framework for Delphi and Lazarus with Lazarus quickstart examples. GitHub identifies an MIT license. Useful API and middleware ecosystem reference for minimal route/middleware ergonomics. Public XPascal API should not become Horse-specific; any design influence must be credited and re-expressed as an XRTL-owned contract. Use as credited design reference only for #42.
Brook / Brook for Free Pascal Brook describes a cross-platform Pascal web microframework; Brook for Free Pascal documents Free Pascal/Lazarus system requirements and third-party support. Brook framework states LGPL-2.1; Brook for Free Pascal states GNU Lesser General Public License. Potential microframework candidate, especially for embedded or compact web apps. Dependency chain and current maintenance fit need proof. LGPL obligations and any Sagui/native dependency packaging must be mapped. Defer until Horse/FCL-Web paths are tested.
mORMot 2 mORMot 2 documents a client/server network layer with HTTP/S, WebSockets, OpenAPI/Swagger, REST router, SOA, and MVC. Disjunctive MPL/GPL/LGPL three-license model. Powerful future server provider or full-stack option. Large integration surface and possible overlap with XRTL.Database, XRTL.HTTP, XRTL.Web, Diagnostics, and Config. Defer; revisit after independent XRTL contracts exist.
Indy Indy repository describes Internet Direct; license page states dual Indy Modified BSD or Indy MPL. Issue/discussion activity exists in 2025-2026. Dual license: Indy Modified BSD or MPL-1.1. BSD path requires attribution. Broad low-level protocol library and possible future network backend. TLS/OpenSSL and FPC integration need dedicated validation. It is lower-level than XRTL.Web. Defer to a networking/TLS-specific issue, not first Web provider.

Wrapper Policy

Database, HTTP, and Web should expose XRTL contracts first. Adapters may use SQLDB, fcl-web, Horse, ZeosLib, mORMot 2, Brook, Indy, or other providers internally only after the provider passes the dependency provenance gate.

Wrapping is justified because XPascal needs stable diagnostics, config, error identity, platform behavior, test harnesses, and generated-project ergonomics independent of any single upstream provider.

Next Implementation Issues

  • Issue #40, XRTL.Database v0: define connection config, transaction, command/query, row/value mapping, and SQLite local smoke over SQLDB only.
  • Issue #41, XRTL.HTTP research: compare FCL-Web and fphttpserver, inspect fork/modification feasibility, and write credit/NOTICE rules before implementation.
  • Issue #42, XRTL.Web middleware: define route matching, middleware order, context, and error-to-response mapping. Credit Rack and Horse as design references.
