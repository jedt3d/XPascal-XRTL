Dependency Provenance Register

Status: issue #27, completed by PR #36, defines this register as the source of truth for third-party dependency and license provenance. Issue #28 adds the source-backed database and web candidate research in XRTL Database And Web Candidate Research.

This register records third-party projects considered, adopted, wrapped, referenced, or rejected by XCLI and XRTL. No third-party source should be copied, vendored, linked, or wrapped before a provenance record exists and the adoption gate below is satisfied.

This document is an engineering register, not legal advice. Treat every license note as a verification checklist against the exact upstream source, release, and artifact before adoption or redistribution.

Current dependency posture: XRTL.Core v0 has no third-party runtime dependency. The project uses the pinned FreePascal 3.3.1 toolchain. Issue #40 narrows Database v0 to local SQLite through SQLDB only. Issue #62 defines ORM V1 as a clean-room plan inspired by SQLModel/SQLAlchemy architecture, and issue #64 implements it without adopting an ORM dependency. ZeosLib remains a provider/component reference rather than an ORM dependency. Issue #41 researches FCL-Web versus fphttpserver before HTTP implementation. Issue #42 designs Web middleware independently while crediting Rack and Horse as references.

Register Rules

  • Prefer maintained projects with clear licenses, active upstreams, and evidence that they work with FreePascal on Windows x86_64, macOS Apple Silicon aarch64, and Ubuntu 26.04 x86_64.
  • Record upstream project name, canonical URL, license source, activity signal, feature fit, cross-platform evidence, attribution/NOTICE duties, and wrap/direct-use rationale.
  • Do not rely on GitHub's license badge alone. Link to upstream license files, release notes, package metadata, or project documentation when they are the source of a claim.
  • Do not copy source from a project whose license status is only guessed or inherited through a mirror.
  • Prefer a wrapper when it protects XRTL contracts, keeps future replacement possible, hides unstable upstream APIs, or prevents dependencies from leaking into public types.
  • Prefer direct use only when the upstream API is already the intended public contract and long-term replacement is not a priority.
  • When license obligations are unclear, keep the dependency in research-only status and open a follow-up issue or ADR before adoption.

Status Model

Status Meaning Allowed In Code?
candidate Interesting enough to track, but not researched deeply enough to choose. No.
research-only Under active evaluation; source links and license hints exist, but no adoption decision is made. No.
prototype-approved May be used in throwaway or branch-local experiments after license source and test scope are recorded. Only in non-merged experiments unless the PR says otherwise.
adopted Approved for repository use with documented license, attribution, packaging, and test obligations. Yes.
wrapped Approved through an XRTL wrapper that hides upstream API details from public contracts. Yes, behind the wrapper boundary.
inspiration-only Useful for design reading, but no source, API, or dependency is adopted. No.
rejected Not suitable because of license, maintenance, platform, security, API-shape, or ownership risk. No.

License Verification States

State Required Evidence
unverified Only a candidate name or secondary source is known.
source-located Canonical upstream repository or package source has been linked.
license-identified Upstream license file or authoritative project documentation is linked.
obligations-mapped Attribution, NOTICE, source redistribution, dynamic/static linking, and modification duties are summarized for the intended usage.
approved-for-use Maintainer accepts the obligations in a PR or ADR, and tests/package impact are recorded.

Adoption Gate

  1. Open or confirm a GitHub issue for the dependency evaluation.
  2. Add or update the candidate row in this register.
  3. Link canonical upstream source and license files.
  4. Record activity signal: latest release, recent commits, issue/PR activity, maintainer notes, or explicit abandonment risk.
  5. Record feature fit and missing capabilities against the XRTL library that would use it.
  6. Record cross-platform evidence for Windows x86_64, macOS Apple Silicon aarch64, and Ubuntu 26.04 x86_64.
  7. Record attribution, NOTICE, redistribution, and source-modification obligations for the intended use.
  8. Choose direct use, wrapper, inspiration-only, reject, or defer; create an ADR if the choice affects public API or architecture.
  9. Only then may an implementation PR copy, link, vendor, wrap, or expose the dependency.
